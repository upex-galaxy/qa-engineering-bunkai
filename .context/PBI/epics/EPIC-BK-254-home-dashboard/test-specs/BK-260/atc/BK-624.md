## 5. Code Template

```typescript
@atc('BK-624')
async verifyActivityItemRenders(args: ActivityItemAssertionArgs): Promise<void> {
  await this.goto();
  const row = this.recentActivityItem(args.eventId);
  await expect(row).toBeVisible();
  await expect(row).toContainText(this.config.testUser.email);
  await expect(row).toContainText(args.expectedActionLabel);
  await expect(row).toContainText(args.expectedItemLabel);
  await expect(row.locator('time')).toHaveText('just now');
  await expect(row.locator('span[aria-hidden="true"] svg')).toHaveClass(new RegExp(args.expectedGlyphClass));
  if (args.expectedChip === 'none') {
    await expect(row.locator('[data-status]')).toHaveCount(0);
  }
  else {
    const status = args.expectedChip === 'Passed' ? 'pass' : 'fail';
    await expect(row.locator('[data-status]')).toHaveAttribute('data-status', status);
    await expect(row.locator('[data-status]')).toContainText(args.expectedChip);
  }
}
```

### Data substitution rationale

The Story's Examples table lists `module.created` and `bug.created` as two of its 5 rows. Neither is in `ACTIVITY_ALLOWED_ACTIONS` (`lib/activity/constants.ts`) — `bunkai_list_activity` filters by this allowlist at the RPC layer (Decision 2), so seeding either action would produce a real `activity_log` row that the feed's own read path silently excludes; the row would simply never appear, making the TC unwinnable as literally written. Substituted:

- `module.created` → **`module.renamed`**: real, allowed action, same `entity_type: 'module'`, and — unlike `module.archived` (also considered) — its `deriveItemLabel` switch case (`app/api/v1/activity/response.ts`) resolves to the module's real NAME (`nonEmptyString(payload.name) ?? fallback`), giving a concrete, assertable item-label value rather than the generic `"a module"` fallback `module.archived`/`module.description_updated` produce. Chosen over `module.moved` for the same reason plus simpler setup (rename = one PATCH call vs. move needing a second module as the destination parent).
- `bug.created` → **`bug.status_changed`**: real, allowed action, same `entity_type: 'bug'`, and exercises the ONE label-placeholder path (`{status}` → "in progress") that doesn't require resolving a second user's email (unlike `bug.assigned`/`bug.reassigned`, which need an `assigneeEmail` lookup — extra setup complexity with no additional partition value, since the placeholder-resolution CODE PATH being tested is the same shape either way: a payload field substituted into the label template).

### EP-merge: `test.created` dropped

The Story's original 5th row (`test.created`, entity_type `test`) is EP-merged into the `module.renamed` row rather than kept as a 5th data row. Justification: `GLYPH_BY_ENTITY_TYPE` (`RecentActivity.tsx`) only special-cases `bug` and `run` — every other `entity_type`, including both `module` and `test`, falls through to the SAME generic accent-box glyph. `deriveItemLabel`'s switch also treats `test.created` identically in SHAPE to `module.renamed` (`nonEmptyString(payload.title) ?? fallback` vs. `nonEmptyString(payload.name) ?? fallback` — same pattern, different field name). Keeping both rows would test the identical code path twice with different literal strings, which test-design-doctrine.md Part 1 Principle 4's anti-padding clause explicitly excludes ("does this case explore something a sibling case does not?" — no). `module.renamed` is kept as the representative because module setup (create + rename) is marginally simpler than test setup (create + chain an ATC), with no coverage cost.

### BVA reduction rationale

Events are created via `POST` calls at test-run time; every endpoint in this chain (`bunkai_bootstrap_workspace`, module/bug/run creation, `bunkai_finish_run`) stamps `created_at = now()` server-side with no API parameter to backdate it. Hitting the "5m ago" or "2h ago" buckets deterministically would require either (a) a real 5-minute/2-hour wait inside the test (unacceptable — turns a fast API-driven precondition into a multi-hour test run, and still races real clock drift), or (b) direct DB manipulation of `activity_log.created_at` after the fact. DBHub (the one tool that could do (b) safely, scoped to a throw-away row) was unavailable this session (`CONNECT_TIMEOUT`), and even with it available, mutating `created_at` directly on shared staging is a heavier-weight, riskier operation than this ticket's other Generate-pattern setup — the same class of gap that led the Story's own TC6 (BK-629, the 24h WINDOW boundary — a sibling BVA case on the same `formatRelativeTime`/`selectRecentActivity` surface) to be filed as `Draft`, not `Candidate`, and therefore excluded from automation entirely by the ticket's own scope. Per test-design-doctrine.md's RISK checklist item, this drop is stated explicitly (here, plus automation-plan.md §7) rather than silently omitted: **the minute/hour buckets of `formatRelativeTime` are NOT live-verified by this ATC pass.** They remain testable at the UNIT level (`lib/home/recent-activity.test.ts`, product repo) — `formatRelativeTime` is a pure function that already accepts an explicit `now: Date`, so a unit test can assert every bucket deterministically without any timing risk; that is a product-repo unit-test gap, not an E2E automation gap, and is called out as an `open_question` (not actioned by this plan — out of this repo's ownership).

**Two reduction axes**:

| Parameterized ATC | Reduction applied | Rows after reduction |
|---|---|---|
| BK-624 `verifyActivityItemRenders` | EP-merge (`test.created` → `module.renamed`) + BVA scope-reduction (minute/hour buckets dropped, "just now" only) | 4 (module, bug, run-passed, run-failed) — down from the Story's 5 |
