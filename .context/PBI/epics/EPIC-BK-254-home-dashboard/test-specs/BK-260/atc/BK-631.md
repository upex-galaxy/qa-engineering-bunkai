## 6. Technique-derivation check

| AC | Technique fired | ATCs produced |
|---|---|---|
| Risk-beyond-AC (RLS scoping, `activity_log_select_workspace_member`) | Decision table (workspace membership × cookie value → visible or not) + Error-guessing (security risk, per the Story's own ATP row "Decision table / security") | BK-631 — one ATC |

**Decision table:**

| Active workspace = event's own workspace? | Caller is a member of the event's workspace? | Cookie names event's own workspace? | Event visible? | Covered by |
|---|---|---|---|---|
| Yes | Yes | Yes | Yes | (out of this ATC's scope — the "normal" case is implicitly covered by BK-624, which asserts a JUST-created event IS visible in its OWN workspace) |
| No | Yes (same user owns both workspaces) | No (cookie names Workspace B) | No | **BK-631** — this ATC's exact construction |
| No | No (literal Gherkin wording: "a workspace she does not belong to") | Forged to name the foreign workspace | Not reachable via the UI/API surface at all | See "Adaptation rationale" below — this row is NOT directly testable |

**Adaptation rationale**: the Story's Gherkin (`test-cases/TEST-BK-631-*.md`) reads "activity events exist in a workspace the QA engineer does not belong to... even with a forged active-workspace cookie". Direct read of `lib/workspaces/active.ts`'s `resolveActiveWorkspaceId`:

```typescript
export function resolveActiveWorkspaceId(cookieValue, visibleWorkspaceIds) {
  if (cookieValue && visibleWorkspaceIds.includes(cookieValue)) return cookieValue;
  return visibleWorkspaceIds[0] ?? null;
}
```

A `bk_active_ws` cookie naming a workspace NOT in `visibleWorkspaceIds` (i.e., a workspace the caller does not belong to) is silently rejected and falls back to the caller's own first workspace — it is never passed through to `fetchActivityPage`/`bunkai_list_activity` as the resolved `workspace_id`. There is therefore no reachable code path, from the browser or a direct API call with a forged cookie, that would even ATTEMPT to read a foreign, non-member workspace's activity through this resolution chain — the RLS policy (`activity_log_select_workspace_member`) is a defense-in-depth backstop for a request shape the app-layer resolver already can't produce. Automating the LITERAL wording would require bypassing `resolveActiveWorkspaceId` entirely (e.g., a raw `?workspace_id=` query param, if the route accepted one for this internal call — it does not; Home's server component calls `fetchActivityPage` directly, no query string) — not a reachable E2E path.

The adapted construction preserves the RISK under test — "can an event from workspace X ever render while workspace Y is active" — with a deterministic, same-user two-workspace setup that IS reachable: Workspace A (source of a real event) and Workspace B (target, active), both owned by the test user, switched via the EXISTING `HomePage.useWorkspace()` cookie helper (unchanged, from HD-T01). This exercises the SAME RLS predicate (`activity_log_select_workspace_member` scopes strictly by `workspace_id`, membership or not is irrelevant to the SQL — it just filters `WHERE workspace_id = p_workspace_id`) without requiring an unreachable "non-member" precondition. If a genuinely non-member scenario becomes reachable in a future ticket (e.g., a debug/admin API), that is a new ATC then, not a retrofit of this one.

**Pairwise**: N/A — 2 factors (source workspace, target workspace), not 3+.

**Two reduction axes**: N/A — not a parameterized ATC (one row, the adapted construction).
